# ADR 00032: pokemon.csv の事実列(genus/rarity/height_m/weight_kg/description)

- Status: accepted
- Date: 2026-07-30
- Supersedes: none
- Superseded by: none

## Context

pokemon.csv は `type1/type2` と `generation` しか属性を持っておらず、カード表示(動画レイアウトの `pokemon_card`)で名前とタイプ配色以外に出せる情報が無い。他リストでは scientist の `description`、plant の `family/genus` のように「事実の付加情報」を持たせている。ポケモンでも同じことをしたい。

情報源の PokéAPI には日本語のフレーバーテキスト(`pokemon_species_flavor_text.csv`。図鑑説明文)もあるが、**これはゲーム本体の文章そのままで著作物**であり、本リポジトリの方針(ADR 00002 で公式アセット・キャラクター造形を収録しないと決めたのと同じ理由)では収録できない。一方で分類名・高さ・重さ・伝説かどうかといった**事実データ**は、同じデータセットの構造化された属性として扱える。

## Decision

- `generation` の後ろに次の列を追加する(`image`/`image_page` は他リストの慣例どおり末尾のまま)

  | 列 | 意味 | 出典 |
  |---|---|---|
  | `genus` | 日本語の分類名(`ねずみポケモン`) | `pokemon_species_names.csv` の `genus`(local_language_id=1) |
  | `rarity` | `伝説` / `幻` / `ウルトラビースト` / `NA` | `pokemon_species.csv` の `is_legendary` / `is_mythical`。UBはフラグが無いため全国図鑑Noの固定リスト(`ULTRA_BEASTS`) |
  | `height_m` | 高さ(m、小数1桁固定) | `pokemon.csv` の `height`(デシメートル)÷10 |
  | `weight_kg` | 重さ(kg、小数1桁固定) | `pokemon.csv` の `weight`(ヘクトグラム)÷10 |
  | `description` | 事実を並べた説明文 | 上記列からの機械生成 |

- **`description` は事実テンプレートのみで機械生成し、公式のフレーバーテキストは取得も収録もしない。** 書式は
  `<genus>。<タイプ>タイプ。初登場は<バージョン対>。[伝説のポケモン。/幻のポケモン。/ウルトラビースト。]高さ<X>m、重さ<Y>kg。`
  - 例(ミュウツー): `いでんしポケモン。エスパータイプ。初登場は赤・緑。伝説のポケモン。高さ2.0m、重さ122.0kg。`
  - 単タイプは「でんきタイプ。」複合は「くさ・どくタイプ。」。`rarity` が `NA` の行は伝説/幻/UBの文を入れない(通常であることは書かない)。世代の数字は `generation` 列にあるので文中には入れない
  - 全行が同じ型の文になるが、出典が構造化データなので**権利上安全で、全件再生成しても揺れない**。文章としての面白さは捨てる
- **`rarity` は通常のポケモンを空ではなく `NA` にする。** pokemon.csv は単タイプを `type2=NA` としており、同じリスト内で「該当なし」の表し方を揃えたい。伝説でも幻でもないことは欠測ではなく確定した事実なので、空(=情報が無い)と区別したい
- **世代→バージョン対はハードコードする。** PokéAPI の `version_names` から引くと第1世代が「赤・青」(海外版の対)になる。日本のリストとしては「赤・緑」が自然なので、`GENERATION_VERSIONS` として各世代の代表2バージョンを持つ(1:赤・緑, 2:金・銀, 3:ルビー・サファイア, 4:ダイヤモンド・パール, 5:ブラック・ホワイト, 6:X・Y, 7:サン・ムーン, 8:ソード・シールド, 9:スカーレット・バイオレット)。新世代の追加時はここに1行足す
- **種レベルの属性(`genus`/`rarity`)はフォーム行も親種の値を継承する。** 分類名や伝説フラグは PokéAPI でも種にしか付いていない
- **高さ・重さはフォーム自身の `pokemon` エントリの値を使う。** メガシンカ・キョダイマックスは本体と別の体格を持つ(メガフシギバナ 2.4m/155.5kg、フシギバナ 2.0m/100.0kg)ため、ここを継承すると誤りになる
- 数値は `6.0` のように**小数1桁で固定して文字列化**し、`description` の中の表記と一致させる

## Consequences

- カード表示や絞り込みで分類名・伝説/幻・体格が使える。`rarity=伝説` のような絞り込みも1列で書ける
- `rarity` の `伝説`/`幻` は PokéAPI の `is_legendary`/`is_mythical` をそのまま使うため、ファン用語の区分とはずれる場合がある(いわゆる準伝説も一律 `伝説`、タイプ:ヌル・シルヴァディも `伝説`)。独自基準は持たない(維持コストが高く、出典が言えなくなるため)。例外は `ウルトラビースト`: PokéAPIにフラグが無いが公式呼称のある区分なので、全国図鑑Noの固定リストで持つ(第7世代で完結した11種の閉集合なので保守コストは無い)
- `description` は 1373 行すべてに入る。フレーバーテキストのような読み物ではなく、事実の列挙であることを前提に使うこと
- PokéAPI の ja-Hrkt に分類名が無い種(第9世代DLCの カミッチュ/チャデス/ヤバソチャ/イイネイヌ/マシマシラ/キチキギス/オーガポン の7種)は、公式サイト(pokemon.co.jp のDLC紹介ページ)等で確認した値の暫定ハードコード(`GENUS_FALLBACK`)で補完する。PokéAPI 側に値が入ればそちらが優先されるので、埋まったらフォールバックは削除してよい。今後フォールバックにも無い未登録種が出た場合は `genus=NA` となり、`description` は分類名の文を落として生成される
- 「〇〇のすがた」の表記ゆれ3行は同じ事実列を共有する(同一ポケモンなので当然)
- 既存列(`id`/`original`/`surface`/`pronunciation`/`type1`/`type2`/`generation`/`image`/`image_page`)の値は変えていない。追加は列の挿入だけなので、列名で読む利用側は影響を受けない(位置で読む実装は影響を受ける)
