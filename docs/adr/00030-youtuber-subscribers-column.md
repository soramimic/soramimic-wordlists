# ADR 00030: youtuber.csv に subscribers(チャンネル登録者数)を追加し、毎回上書きする

- Status: accepted
- Date: 2026-07-30
- Supersedes: none
- Superseded by: none
- Related: 00014(既存行を劣化させない・空欄補完のみ) / 00023(debut_year をチャンネル開設年で補う) / 00029(channel・description 列。メインチャンネルの定義)

## Context

youtuber.csv には「その人がどれくらい有名か」を表す数値が無い。利用側(ソラミミック)で
**知名度順に出題を並べたい・マイナーすぎる人を除きたい**という用途があるのに、
今ある手掛かりは org(所属)と debut_year だけで、YouTuber の規模を直接表す列がない。
ADR 00029 でメインチャンネル名を入れたので、その規模を並べて置くのが自然である。

候補は2つあった。

**(a) Wikidata の登録者数(P3744)**。P2397(チャンネルID)の修飾子として入っており、
ADR 00029 のメインチャンネル選定にも既に使っている。追加の通信は要らない。
しかし**値の記録時点(P585)が項目ごとにバラバラ**で、横に並べて比較できない。
実測(対象972人のうちQIDあり963人、2026-07時点):

| P585(記録時点)の年 | 人数 |
|---|---|
| 2019 | 1 |
| 2020 | 124 |
| 2021 | 94 |
| 2022 | 106 |
| 2023 | 106 |
| 2024 | 146 |
| 2025 | 91 |
| 2026 | 31 |
| 記録時点なし | 5 |

P3744 を持つのは686人いるが、**2026年の値があるのは31人だけ**である。
2020年の登録者数と2026年の登録者数を同じ列に混ぜると、「登録者数で並べる」という
唯一の用途がそのまま壊れる。しかも Wikidata 側の更新はボランティア任せなので、
待っていても揃わない。

**(b) YouTube Data API v3 の `channels.list(part=statistics)`**。全チャンネルの
登録者数を**同じ時点のスナップショット**として取れる。`id` に最大50件を並べられ、
クォータは1リクエスト=1ユニット(1日10000ユニット)なので、923本を取るのに19
ユニットしか要らない。月1回のバッチには十分な余裕がある。

## Decision

1. **`subscribers` 列 = YouTube Data API から取った登録者数(整数の文字列)**。
   Wikidata の P3744 は使わない((a)の理由)。列は既存ファイルの末尾に足す
   (利用側は列名で読むので位置は問わない)
2. **チャンネルIDは Wikidata の P2397 から引く**。取り消し済み(DeprecatedRank)の
   文は除く(ADR 00029 の channel 取得と同じ扱い)。書式が `UC` + 22文字に
   合わない値(URL やユーザー名の誤登録)は API に投げる前に弾く
3. **1人が複数チャンネルを持つ場合は、その人のチャンネル群で最大の登録者数を採る**。
   channel 列の「登録者数が最大の1本をメインチャンネルとみなす」定義(ADR 00029)と
   同じ基準なので、`subscribers` は原則 `channel` の登録者数になる
4. **登録者数を非公開にしているチャンネル(`hiddenSubscriberCount`)は候補から除く**。
   1本も取れなければ `NA`。QIDが無い行も `NA`
5. **毎回全行を上書きする**。**これは「既存値を書き換えない」(ADR 00014)の明示的な
   例外**である。ADR 00014 は表記・読み・分類のような**確定値**が自動更新で劣化する
   のを防ぐためのもので、登録者数は本質的に**時変値**なので、古い値を残すことに
   意味がない(むしろ「いつの値か分からない列」になり、(a)で却下した問題を
   自分で作り込むことになる)。列の意味を「最後にバッチが走った時点の登録者数」に
   固定する
6. **実装は専用スクリプト `tools/update_youtuber_subscribers.py`**(単独実行可能)。
   `update_youtuber.py` に混ぜない。理由は3つ:
   - 唯一の外部APIキー(`YOUTUBE_API_KEY`)が要る処理なので、キー無しでも動く
     Wikidata 経路と分けておきたい(キーが無ければ「スキップ」で正常終了する)
   - 上書き規則が update_youtuber の「空欄補完のみ」と正反対なので、同じループに
     入れると規則が読み取れなくなる
   - クォータ超過で落ちたときに youtuber.csv の追記まで巻き戻したくない
7. **書き込みは全チャンネルの取得が成功してから最後に1回だけ**。途中で失敗した回は
   youtuber.csv を一切書かない(書きかけを残さない)。さらに、登録者数が取れた人が
   300人を下回った回は「取得が壊れている」とみなして**書かずに非0終了**する
   (毎回上書きする列なので、取得障害で既存値を `NA` に潰す事故を防ぐ)
8. **月次バッチに組み込む**(`Update youtuber.csv` の直後、`continue-on-error`)。
   失敗時の巻き戻し(`revert_if_failed`)には**ファイルを指定しない**。7 により
   書きかけは残らず、逆に youtuber.csv を巻き戻すと同じ回の `update_youtuber` の
   追記まで消えてしまうため
9. **APIキーはログに出さない**。取得は環境変数 `YOUTUBE_API_KEY`、無ければ
   `~/.config/soramimic/youtube_api_key`。例外メッセージやレスポンス本文に
   混ざる可能性があるので、出力は必ず `_redact()` を通す

## Consequences

- 実行結果(2026-07-30、972人): P2397 のチャンネルは923本/711人ぶんあり、そのうち
  911本の登録者数が取れて、**706人(73%)** の `subscribers` が埋まった
  (1494/2020行)。取れなかった12本は削除・BAN済みのチャンネルで、静かにスキップ
  している。非公開(`hiddenSubscriberCount`)は0本だった。既存列の値は1つも
  変わらず、差分は新列の書き込みだけ
- 充足率の上限は **Wikidata に P2397 があるかどうか**で決まる(711/963人)。
  API 側で取りこぼしているわけではないので、増やすには Wikidata 側の充実を待つか、
  チャンネルの別経路での同定が必要になる
- **値は概数(有効数字3桁)**。YouTube は2019年以降、登録者数を丸めて公開している
  (例: 826aska = 901000、HIKAKIN = 19800000、兎田ぺこら = 2780000)。
  **正確な人数ではないので、桁の比較・並べ替えに使うこと**。差が1%以内の2人の
  順位は意味を持たない
- 短時間に2回実行しても丸めの範囲で同じ値になる(冪等の確認として2回連続実行し、
  値が変わった人0人を確認した)。一方で**月次バッチでは毎回ほぼ全員の値が動く**
  ので、自動更新PRの差分に700行前後の数値変更が常に出る。これは仕様であり、
  差分レビューでは「subscribers 以外の列が動いていないか」を見ること
- **リポジトリシークレット `YOUTUBE_API_KEY` の設定が必要**。未設定のままでも
  バッチは壊れず、このステップだけがスキップされる(fork でも同じ)。キーは
  YouTube Data API v3 を有効にした Google Cloud プロジェクトの API キー
- 出典が1つ増える(YouTube Data API v3)。登録者数は YouTube が公開している
  事実値で、CSV には数値だけを入れる
